Amped Up Music Promotions — V1 Build Plan
1. Technical architecture

I recommend this stack:

Area	Choice
Frontend	Astro + TypeScript
Hosting/runtime	Cloudflare Workers + Static Assets
Database	Cloudflare D1
Images/posters	Cloudflare R2
Admin authentication	Cloudflare Access
Bot protection	Cloudflare Turnstile
Payments	SumUp Hosted Checkout
Transactional email	Provider abstraction; initially Resend
QR tickets	Generated by Amped Up
Door scanner	Browser camera/PWA-style /admin/door
Tests	Vitest + browser/E2E tests
Source	GitHub

Cloudflare now recommends Workers Static Assets rather than Pages for new projects, and Astro is a first-class supported framework. Astro is particularly appropriate because the public site can remain mostly server-rendered HTML with JavaScript only for things such as checkout, admin controls and the QR scanner.

D1 is Cloudflare's serverless SQLite database and R2 can be bound directly to the Worker, so this can remain a fairly compact Cloudflare deployment.

2. Site structure

The public website should have:

/ — next-event hero, upcoming events, recent photographs, selected social content and clear ticket CTA.
/gigs — all upcoming promotions.
/gigs/[slug] — individual event.
/tickets — current ticket availability across gigs.
/past-gigs — automatically populated archive.
/past-gigs/[slug] — event history/gallery.
/gallery — photographic event archive.
/artists and optionally /artists/[slug].
/venues if useful once they have several regular venues.
/about.
/promote-with-us — artist/venue enquiry.
/contact.
/privacy.
/ticket-terms.
/accessibility.
/admin/* — completely protected management application.

The event page is the core object. Almost everything else should derive from that rather than being independently maintained.

AMPED-06 — Ticket Inventory and Orders

Owner: DeepSeek

This slice is important enough to finish before SumUp is connected.

Build the internal purchasing system against a fake payment provider first.

Flow:

Choose event → ticket type → quantity → buyer name/email → terms → create order → reserve inventory → payment provider

Prevent overselling atomically.

A checkout creates a temporary reservation.

SumUp Hosted Checkout sessions currently last 30 minutes, so our reservation model should correspond to that lifecycle.

For example:

50 available

Buyer A reserves 2.

Immediately:

48 available

Payment succeeds → 2 become sold.

Checkout expires/fails → 2 return to inventory.

A scheduled cleanup plus lazy reconciliation can release expired reservations.

Acceptance: concurrent simulated purchasers cannot exceed event capacity.

AMPED-07 — SumUp

Owner: DeepSeek, tightly supervised

Only now connect the real payment provider.

The Worker creates the SumUp checkout server-side, keeping credentials away from the browser.

SumUp returns a Hosted Checkout URL; the purchaser is redirected there. SumUp then redirects back to Amped Up, while the backend independently confirms the payment result.

Do not trust a browser return such as:

?payment=success

as evidence of payment.

SumUp's own documentation instructs webhook recipients to verify the actual event through the API.

Therefore:

SumUp webhook → Amped Up receives checkout ID → server queries SumUp → confirmed paid → issue tickets

Webhook handling must be:

authenticated/verified through SumUp;
repeatable;
idempotent;
safe against duplicated callbacks;
tolerant of unknown future events.

No card data ever enters D1.

Acceptance: test payment → verified SumUp transaction → exactly one completed order.

AMPED-08 — QR Tickets and Email

Owner: DeepSeek

Once payment becomes confirmed:

create individual ticket records;
generate cryptographically random ticket tokens;
store only what is necessary;
generate QR code;
send customer confirmation;
make ticket available from order confirmation page.

Don't put customer PII in the QR code.

The QR should essentially represent an opaque admission credential.

Example ticket:

AMPED UP MUSIC PROMOTIONS

The Glass Hearts
Saturday 14 November
The Example Venue

Doors 19:30

General Admission

AMP-26-00814

[QR CODE]

Email

I would abstract this behind something like:

TicketEmailProvider

rather than coupling the application to one vendor.

Resend is a sensible initial provider; Cloudflare even has an official Workers integration guide.

That lets us change provider later without changing the ticket system.

Acceptance: successful purchase produces one email containing the correct tickets exactly once.

Features I would deliberately postpone

V1 should not contain reserved seating, native iOS/Android apps, automated artist payouts, automatic social posting, complicated coupons, dynamic pricing, loyalty points, marketplace/resale, merchandise fulfilment or detailed accounting.

Possible V1.1 additions are far more interesting once they have real customers: promo codes, Apple/Google Wallet tickets, promoter analytics, referral links for individual bands, mailing-list segmentation, artist self-submission, repeat-customer stats and merchandise.

How I'd divide the AI work

I think your proposed combination is particularly well suited to this.

Claude Opus gets one relatively large early mission: understand the brief, establish the visual language, scaffold the complete public/admin UX and demonstrate it using mock data. Claude can be encouraged to make design improvements and challenge our visual assumptions.
