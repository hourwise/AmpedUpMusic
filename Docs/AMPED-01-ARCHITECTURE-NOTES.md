### Three decisions that differ in mechanism (not in intent)

These are implementation details the governing plan could not have anticipated, because the relevant
libraries changed after it was written. None of them alters the architecture it specifies.

**1. Bindings are not read from `Astro.locals.runtime.env`.**
`@astrojs/cloudflare` 14 (Astro 7) has **removed** `Astro.locals.runtime.env`. Bindings are now read
inside server-only modules with `import { env } from 'cloudflare:workers'`. This is better for this
project than the alternative: rather than threading `env` through every page, `src/services/index.ts`
is the single module that will ever touch a binding, and no page signature changes when D1 arrives.
Pages call `getServices()` with no arguments today and will still call `getServices()` after AMPED-03A.

**2. Astro 7 uses a strict Rust compiler.**
Unclosed tags and semantically invalid HTML are now errors rather than being silently corrected. This
is a benefit — it is a permanent guard against the malformed markup that breaks screen readers — but
DeepSeek should expect build failures rather than silent fixes.

**3. `output: 'server'` with selective prerendering.**
Four genuinely static pages (`/contact`, `/privacy`, `/promote-with-us`, `/ticket-terms`) opt in with
`export const prerender = true`. Everything that reads data is server-rendered, because prerendering
a page that reads D1 at build time will not work once the database exists. AMPED-03B should revisit
this once caching strategy is decided.

### Layering

```
src/pages/          route + page composition. Calls getServices(). Never imports src/data.
src/layouts/        BaseLayout -> SiteLayout | AdminLayout | DoorLayout
src/components/     presentational only. Receive view models as props. No data access at all.
src/services/       contracts.ts (interfaces) + mock/ (fixture impls). THE SEAM.
src/lib/            pure functions: money, dates, availability, text, seo, site config.
src/types/          domain.ts (storage shapes) + view.ts (joined, presentation-ready shapes).
src/data/           fixtures. Imported ONLY by src/services/mock. Deleted in AMPED-03A.
```

The rule that matters: **components never reach for data.** A page asks a service for a view model and
passes it down. `tests/services.test.ts` is written against the service contracts, not against the
fixtures, so it should keep passing unchanged when the D1 repositories replace them — and if it does
not, the replacement has changed behaviour the UI depends on.

## 2. Assumptions made

These were not specified and had to be decided. Each is cheap to reverse.

1. **Domain and brand.** `ampedupmusic.co.uk`, operating across the North West, is invented. Real
   values live in `src/lib/site.ts` — one file to change.
2. **Two named operators.** Referred to as Anya and Jay in fixture audit entries. The build plan
   mentions "Anya and your son".
3. **No booking fees.** Modelled (`Order.feeInPence`) but set to zero and stated as a selling point on
   the public site. If the business wants fees, the field exists; the copy would need revisiting.
4. **Money in GBP only.** `Pence` is a British integer. Multi-currency is not V1.
5. **Availability thresholds.** "Selling fast" at ≤35% of allocation remaining, "Last few" at ≤12% **or**
   ≤10 tickets absolute. Proportional so a 90-capacity cellar and a 480-capacity hall behave sensibly
   under the same rule. Tunable constants at the top of `src/lib/availability.ts`.
6. **Exact remaining counts are never published.** The public layer sees a coarse state, never a number.
   Publishing "7 left" invites scraping, creates pressure selling, and tells competitors how the night
   is going.
7. **A gig is "past" four hours after the advertised start** when no curfew is recorded. A night must
   not drop into Past Gigs at 19:31 because the first band walked on.
8. **All times display in Europe/London,** stored as UTC. One formatter module, tested against BST.
9. **Dark theme only, no light mode.** It is a gig listing and Door Mode is used in a dark room at
   midnight. `color-scheme: dark` is declared so native controls follow.
10. **Artist pages (`/artists/[slug]`) were built** although the plan lists them as optional. They cost
    almost nothing once the records exist and give each band a page to link to from their own socials —
    free promotion pointing back at ticket pages.
11. **Placeholder artwork is generated, not photographed.** `scripts/generate-artwork.mjs` produces 43
    abstract stage-lighting SVGs at the real poster (3:4) and hero (16:9) ratios. Self-contained, no
    third-party image host, no unlicensed photographs, and honest about being a slot. Deleted in AMPED-05A.
12. **Event titles are not baked into poster artwork.** Typography is HTML over the image, so the type
    system is consistent and an SVG loaded via `<img>` cannot fall back to a random condensed face.
13. **Legal copy is a working draft.** `/privacy` and `/ticket-terms` describe what the system actually
    does. They are marked as drafts on the page and must be reviewed before the site takes money.

## 3. Risks

Ordered by what would hurt most. Each names the slice that must address it.

### Critical — money and admission

**R1. Ticket overselling.** *(AMPED-06B, AMPED-06C)*
The failure mode is two buyers passing the last ticket between them. Mitigated in the design by making
`reserved` count against availability immediately: `available = capacity − sold − reserved`, enforced in
one place (`inventoryFor`) and tested. The real fix is a **single conditional UPDATE in D1** that
decrements stock only if stock remains, never a read-then-write. The acceptance test must be concurrent,
not sequential.

**R2. Payment verification.** *(AMPED-07C, AMPED-07D)*
A browser returning `?payment=success` is not evidence of payment. Encoded in the type system: the
`OrderStatus` doc comment states `paid` may only be entered from a server-side confirmation read back
from SumUp, and `PaymentProvider.confirm()` exists specifically so the webhook path and the return path
both go through it. **This is the single most expensive thing to get wrong** — it is how a site gives
away free tickets.

**R3. Webhook idempotency.** *(AMPED-07C)*
SumUp will retry. A duplicate webhook must not issue a second set of tickets or send a second email.
Needs a processed-webhook table keyed on the provider event id, and an order state machine where
`paid → paid` is a no-op rather than a re-issue.

**R4. Concurrent door scanning.** *(AMPED-09B)*
Two phones, same QR, same instant, must produce exactly one `valid` and one `already-used`. The
`DoorService.checkIn` contract says so explicitly, and the fixture implementation carries a doc comment
stating it is **not** atomic so nobody mistakes it for the real thing. Same single-conditional-UPDATE
discipline as R1.

**R5. QR ticket replay.** *(AMPED-08B, AMPED-09B)*
A screenshotted ticket forwarded to five friends. Mitigated by one-scan-per-ticket at the door rather
than by trying to make the code unforwardable. Tokens must be cryptographically random, stored hashed,
and carry no PII — a photograph of a ticket must tell a stranger nothing about its owner.

**R6. Administrator authorisation.** *(AMPED-04A, AMPED-11)*
Cloudflare Access protects `/admin/*`. Two things commonly go wrong: (a) the Access JWT is trusted
without server-side verification, (b) an API route is created outside the `/admin` prefix and is
therefore public. `tests/services.test.ts` asserts every admin nav entry lives under `/admin`; AMPED-04A
must extend that to every endpoint.

**R7. Email duplicate delivery.** *(AMPED-08C)*
Two confirmation emails is a support cost; two "your gig is cancelled" emails is worse.
`TicketEmailProvider` takes an `idempotencyKey` and returns `deduplicated` for this reason.

### Serious — operational

**R8. Event lifecycle and deletion.** *(AMPED-04B, AMPED-10C)*
The build plan is explicit and the UI already enforces it: an event with orders can never be
hard-deleted, only cancelled or archived. The edit screen disables Delete and explains why. The API
must enforce it too — the UI is a courtesy, not a control.

**R9. Cancelled and postponed gigs.** *(AMPED-10C)*
The commercially dangerous case is a cancelled gig that still sells tickets. Handled in
`deriveAvailability` via `eventSellable`, which returns `unavailable` regardless of stock, and tested.
Postponement keeps tickets valid; cancellation refunds. Refunds stay in SumUp in V1 — building refund
machinery is a large financial risk for little gain.

**R10. Image upload handling.** *(AMPED-05A)*
Type and size checks server-side, safe generated keys (never the uploaded filename), and **alt text as a
required field**. The admin UI already presents alt text as required with the image beside it; the
publish check must enforce it.

**R11. Operator usability.** *(AMPED-12, AMPED-13)*
The real risk to this project is not a bug — it is that the admin is subtly too complicated and the
operators quietly go back to asking a developer. The build plan has the right test: if the operator
guide gets long, the admin is too complicated. Create Promotion is four steps named after things a
promoter says out loud.

**R12. Mobile usability.** *(throughout)*
Instagram → event page → ticket is the dominant journey. Mitigations already in the scaffold: the
Tickets button never folds into the burger menu at any width; the ticket panel sits immediately after
the description on a phone; a sticky buy bar reappears once the hero scrolls away; every control is
≥44px.

### Watch

**R13. Fixture rot in the scaffold.** Fixture dates are offsets from today, so the demo never goes stale.
**R14. Google Fonts as a third-party runtime dependency.** Should be self-hosted in AMPED-11.
**R15. Reservation cleanup.** Expired reservations must be released by both a scheduled sweep and lazy
reconciliation on read — a cron alone will eventually miss one. *(AMPED-06B)*
**R16. Astro 7 compiler strictness.** Malformed markup now fails the build rather than being corrected.

## 5. Ambiguities and conflicts found in the governing plan

No internal contradictions were found. Four points were under-specified and are recorded here for the
supervisor rather than being silently decided:

1. **Order confirmation page has no route.** AMPED-08 says tickets should be "available from order
   confirmation page" but the site structure in §2 does not list one. See V1-1.
2. **`/venues` is conditional** ("if useful once they have several regular venues"). Not built; fixtures
   contain four venues, so the condition is arguably met. See V1-3.
3. **`/artists/[slug]` is marked optional.** Built anyway — see assumption 10.
4. **Guest list capacity is unspecified.** Modelled as a hidden, zero-priced ticket type, which means
   guests are ordinary tickets that scan like everyone else and do not consume public allocation. This
   seems clearly right but was a decision, not an instruction.

## 6. What is deliberately NOT built

Per §16 of the AMPED-01 brief, and verifiable by inspection:

- No D1 migrations, no SQL, no persistence of any kind
- No R2 uploads; `public/media/*.svg` are committed generated files
- No Cloudflare Access middleware; `Astro.locals.operator` falls back to a hard-coded demo identity
- No SumUp code, no credentials, no checkout, no webhook handler
- No email sending of any kind
- No QR generation and no QR verification
- No check-in concurrency control (the fixture door service says so in its own doc comment)
- No mailing-list delivery
- No deployment; `wrangler deploy` has never been run

Every inert control that looks finished carries a `ScaffoldNote` naming the slice that implements it.
`grep -rn "ScaffoldNote\|data-mock" src/` enumerates them.

## 7. For the supervisor

Read before DeepSeek starts:

1. **The binding access pattern changed** (§1, item 1). Any DeepSeek instruction that says
   `Astro.locals.runtime.env` will not work on this stack.
2. **R1, R2 and R4 are the whole project.** Overselling, payment verification and double admission are
   the three failures that cost real money or real embarrassment. Their slices deserve the tightest
   review.
3. **`tests/services.test.ts` is a contract, not a fixture test.** It should survive the D1 swap
   unchanged. If DeepSeek edits it to make a slice pass, that is a scope violation.
4. **Nine V1 recommendations need a yes or no** before the plan is frozen (V1-1 … V1-9). They are
   costed in the DeepSeek build plan but are marked optional; I have not assumed approval.
5. **Legal copy is placeholder.** `/privacy` and `/ticket-terms` must be reviewed by someone qualified
   before the site takes money.
